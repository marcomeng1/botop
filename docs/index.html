BotOp

The robot operation layer of the LIS lab: one small C++/Python interface that drives real robots (Franka Panda, Robotiq, RealSense, OptiTrack) or a PhysX simulation of any model, with exactly the same code.

C++ & Python (import robotic) spline-based motion sim ⇄ real with one flag open-loop plans or closed-loop vision → control built on rai (KOMO, kinematics) reproducible build with pixi

The idea in one pictureYou plan in your own model of the world; BotOp makes the robot (or the simulator) follow.

🧭 Commands are splines

You send waypoints (+ timing). BotOp turns them into a smooth cubic spline that a fast controller tracks. Calls return immediately.

🔁 Sim and real are the same API

BotOp(C, false) starts a PhysX simulation thread; BotOp(C, true) connects the drivers. Your script does not change.

🧩 Hardware chosen by the model

Drivers are picked from frame names in the .g file (l_panda_base → Franka, l_robotiq_base → Robotiq, …).

Each tick, the robot thread asks the reference for q_ref, qDot_ref at the current control time, tracks it, and writes the measured q, qDot into state. Your program only touches the reference and reads the state.

How a motion command worksAll motion commands end up as one cubic spline in the reference buffer.

Which command when?

calluse it when
moveTo(q, timeCost)one target pose; duration is optimized (higher timeCost = faster)
move(path, {T})a path whose total duration T you know (waypoints equally spaced)
move(path, times)you know the time of every waypoint
moveAutoTimed(path, vMax, aMax)a fine path (e.g. from KOMO); duration chosen from velocity/acceleration limits
hold(float, damp)no spline: hold position, float under gravity compensation, or damp

What happens inside

1
Missing timing and waypoint velocities are filled in by a small timing optimization (rai/Control/timingOpt).
2
The result is appended to (or overwrites) the BSplineCtrlReference.
3
The control thread evaluates the spline every tick and tracks it (PD + gravity compensation on the Franka; position control in PhysX).
4
The call returned right after step 2: getTimeToEnd() < 0 tells you the buffer is empty.

The typical main loopSense → plan → act, and keep your model in sync while the robot moves.

Closed loop: from vision to controlBecause commands are non-blocking and can overwrite the running spline, the same structure runs perception → control in a continuous loop (visual servoing, tracking, MPC).

A · Reactive target

Each cycle: perceive the target, solve a small IK, steer there. The simplest form of visual servoing.

bot.moveTo(q, timeCost, true)

The timing is re-optimized from the current reference every call. Higher timeCost means more aggressive.

B · Step control

An RL-style interface: observe, then apply a joint-space delta with a time constant lambda.

obs = bot.stepObservation()
bot.stepAction(delta, obs, lambda)

Writes a constant-acceleration spline piece (acceleration clipped by maxAccel). Example: 05-moveTo, test_reactive_control.

C · Model-predictive control

Re-plan a short path (and its timing) every cycle and overwrite the future part of the spline.

bot.move(path, times, true, ctrlTime)

07-leapCtrl (ShortPathMPC + timing optimization); 13-reactiveGrasp with skills/control/SecMPC_Stepper for whole multi-phase tasks.

Sketch: camera-driven reaching (Python, runs in simulation with a stand-in detect)

import robotic as ry

C = ry.Config()
C.addFile(ry.raiPath('../rai-robotModels/scenarios/pandaSingle.g'))
target = C.addFrame('target').setShape(ry.ST.marker, [.1])
bot = ry.BotOp(C, useRealRobot=False)

def ik(C):                                  # 1-step KOMO: gripper at target
    komo = ry.KOMO(C, 1, 1, 0, False)
    komo.addObjective([], ry.FS.jointState, [], ry.OT.sos, [1e-1], C.getJointState())
    komo.addObjective([], ry.FS.positionDiff, ['l_gripper', 'target'], ry.OT.eq, [1e1])
    ret = ry.NLP_Solver(komo.nlp(), verbose=0).solve()
    return komo.getPath()[0] if ret.feasible else None

while bot.getKeyPressed() != ord('q'):
    bot.sync(C, .05)                            # 20 Hz: C <- robot state
    rgb, depth, pts = bot.getImageDepthPcl('cameraWrist', globalCoordinates=True)
    p = detect(rgb, pts)                         # your vision: pixel -> 3D point
    if p is None: continue
    target.setPosition(p)
    q = ik(C)
    if q is not None:
        bot.moveTo(q, timeCost=5., overwrite=True)

detect is yours (color blob, ArUco, a network …). In C++, skills/perception/sense_HsvBlob does the detect-and-set-frame step for a colored blob.

Things to keep in mind

  • An overwriting spline must start near the current reference. moveTo and stepAction handle this; for move, pass bot.get_t() and drop waypoints that are already in the past (as 07-leapCtrl does).
  • Images are older than the robot state. For fast targets, use the camera pose of C at capture time, or predict.
  • Rendering simulated cameras is slow, so read images every few cycles, as 20-simulation does.
  • 13-reactiveGrasp closes the loop on OptiTrack (or a simulated moving ball). For a camera-based loop, combine a detector from 15/senseHsvBlob with pattern A, B or C.

How BotOp picks the hardwareNo configuration code: the frame names in your model decide which drivers start.

To add a robot: put its model in rai-robotModels, test it in simulation (no driver needed), then write a driver in src/<MyArm>/ and register its base frame name. bot.cpp, Python and the bot tool need no change. Step-by-step guide: README section “Adding a new robot arm or hand”.

Quick startSame program in C++ and Python. Flip one flag to run on the real robot.

# once
git clone --recurse-submodules git@github.com:marcomeng1/botop.git && cd botop
pixi run install-all
pixi run bot -help            # the bot tool: home, open/close gripper, float, ...
pixi run bot -sim -loop       # first check: the simulated arm moves back and forth
import robotic as ry

C = ry.Config()
C.addFile(ry.raiPath('../rai-robotModels/scenarios/pandaSingle.g'))

bot = ry.BotOp(C, useRealRobot=False)     # True on the robot (pixi run -e hw ...)

q = bot.get_qHome()
q[1] -= .5
bot.moveTo(q, timeCost=1.)                 # returns immediately
bot.wait(C, forKeyPressed=False, forTimeToEnd=True)   # sync C + viewer until done

bot.gripperClose(ry._left)
bot.wait(C, forKeyPressed=False, forTimeToEnd=False, forGripper=True)

bot.home(C)
del bot
#include <BotOp/bot.h>

int main(int argc, char** argv){
  rai::initCmdLine(argc, argv);

  rai::Configuration C;
  C.addFile(rai::raiPath("../rai-robotModels/scenarios/pandaSingle.g"));

  BotOp bot(C, rai::getParameter<bool>("real", false));   // -real true on the robot

  arr q = bot.qHome;
  q(1) -= .5;
  bot.moveTo(q, 1.);                      // returns immediately
  bot.wait(C, false, true);                 // sync C + viewer until done

  bot.gripperClose(rai::_left);
  bot.wait(C, false, false, true);

  bot.home(C);
  return 0;
}

The real-robot run needs the hw environment plus a one-time OS setup (real-time kernel, udev rules, network to the arm): see the README section “Run on hardware”. Press q in the viewer to leave a wait.
